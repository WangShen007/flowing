# 飞书权限核对（2026-09-08）

## 范围与当前状态

网站已审核 49 个操作、23 类能力。按本机 lark-cli 1.0.93 与官方同版本源码核对基础及条件依赖，普通员工 onboarding 40 scopes，负责人/管理员 42 scopes（含 offline_access）。

当前保存的有效用户授权相对新清单缺：

- `im:chat.members:read`：群成员读取。用户截图明确显示应用后台未开通（20027）。
- `wiki:node:retrieve`：文档更新含本地资源、导入到特定知识库目标时的条件依赖。当前用户授权未包含；应用后台是否已开通尚未核实。

后续通过用户已登录的 Chrome 核实了应用 ID 与服务配置一致。后台导出原有 43 项用户身份权限、35 项应用身份权限，对比网站 42 项清单仅缺上述两项。已通过后台逐项新增这两项**用户身份权限**；两者为免审权限，新增后分别核实显示“已开通”“与用户权限范围一致”，页面显示“当前修改均已发布”。未新增任何应用身份权限、未关闭原有权限、未改成员角色或数据范围。用户的增量授权和只读实测仍需另行完成。

## 角色和数据边界

| 能力 | 普通员工 | 负责人 / 网站管理员 |
|---|---|---|
| 本人可访问的文档、消息、群与成员、日程、任务、会议、妙记、多维表格读取 | 允许 | 允许 |
| 发消息、编辑文档、安排日程、更新任务和表格 | 允许，写操作确认 | 允许，写操作确认 |
| 创建项目群、管理项目任务清单 | 不允许 | 允许，写操作确认 |
| 任意删除、共享权限管理、审批代办、切换机器人身份或其他账号 | 未纳入执行清单 | 同样未纳入执行清单 |

网站角色取自 account_memberships，**没有自动同步飞书企业职级**。新登录用户默认 employee，不依据姓名、头衔或模型判断提升权限。未知角色拒绝授权。

业务执行使用当前账号的用户 token、企业租户校验和用户身份严格模式，每次执行重查当前网站角色及 grant。不使用管理员 token 兜底。实际数据范围仍由飞书资源 ACL、企业策略和接口可见性约束；网站管理员不因此能读取其他人的私有资源。普通成员读取保密群/未共享文档不能靠补 scope 绕过。

## 本轮修复

- 注册文档创建/更新与导入的条件依赖，纳入角色 onboarding 和按操作增量授权。
- 基础调用不使用附件/知识库功能时，仍按基础 scopes 校验。
- 原生群成员查询要求 `check_security_conf=true`，模型 schema 固定为 true，执行层再次检查内联 JSON，重复参数亦不能关闭检查。
- 仅授权查询可以不携带业务参数，该模式不用于执行 CLI。
- 未知角色 fail closed；保留正常员工读取能力，不改变现有员工/负责人映射。

`base:table:delete` 是官方 `+base-create` 的声明依赖，不等于网站开放任意删除 API。

后续发送实测纠正：仅 `im:message.send_as_user` 不足以覆盖当前 CLI 调用的 `/im/v1/messages`，执行 64/65 返回 99991679。已按官方 CLI UserScopes 补入 `im:message`；不申请机器人发送权限，不切换身份。此变更使网站角色清单各增加一项，仍需核实应用后台的用户身份授权并由用户增量授权。此前“基础发送授权已齐”的结论不成立。

## 后续验收

1. 应用管理员登录开发者后台；按 `scopes_for_role('admin')` 核对用户身份权限及已发布版本，补缺项，不增加无关 tenant/bot 权限。
2. 完成必要的应用发布/企业审批后，由用户在网站完成增量授权。
3. 只读验收群成员；知识库依赖用用户已获授权的资源验证。不要发送通知作为权限测试。
4. 不同企业身份的真实 ACL 隔离仍需对应测试账号验证；单管理员测试不能证明所有成员都可访问。
